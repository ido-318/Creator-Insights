# אבטחה והקשחה — 16.10.2026

בוצעה סריקת הקוד הנוכחי באמצעות Codex Security, עם ביקורת בסיס עצמאית, סקירת ארכיטקטורה ובדיקה ממוקדת. נמצאה חולשת גישה מקומית אחת בחומרה נמוכה ותוקנה. נוסף חיזוק בכמה שכבות. הסטטוס `partial` מציין התראות תלויות ובדיקות ענן שנותרו, ולא כשל בבדיקות התיקון.

## הממצא שתוקן

**CWE-306 — גישה ללא אימות לממשק המקומי.** לפני התיקון, משתמש אחר באותו מחשב יכול היה להתחבר ל־127.0.0.1:8501, לקרוא דוחות, לשנות עיצוב ולהפעיל את ה־Flow בתהליך ובמפתח ה־API של בעל הפרויקט. קישור ל־localhost מגביל מחשבים אחרים, אך אינו מזהה את חשבון מערכת ההפעלה. ההרשאות הפרטיות של תיקיית הפרויקט אינן מגינות על ממשק HTTP פתוח.

החומרה נמוכה בהקשר הנוכחי: נדרש משתמש מקומי לא מהימן ושרת פועל. לא הוכחה חשיפה לאינטרנט, לא בוצע ניצול חי ולא נטען שקיימת הרצת פקודות שרירותית. השימוש ב־Supabase מותנה בהגדרתו. קובץ המקור העיקרי לפני התיקון: `app.py:263–269`.

**התיקון:** שער כניסה בתחילת `app.py`, לפני קריאת נתונים, חיבור ענן, הורדות או פעולות. הקוד נבדק בהשוואה בזמן קבוע; הסשן שומר טביעת קוד ולא את הקוד עצמו. קוד שגוי/קצר או כשל בתצורה חוסמים גישה. יציאה מנקה את הסשן; החלפת קוד פוסלת סשנים ישנים בפעולה הבאה. זהו מפתח משותף למפעיל מקומי, לא ניהול משתמשים נפרדים.

## כניסה, הפעלה והחלפת קוד

1. הפעילו מתוך תיקיית הפרויקט: `python -m streamlit run app.py`.
2. פתחו מקומית את `.streamlit/access_token` והעתיקו את הקוד לשדה הכניסה. הקובץ נוצר אוטומטית מקלט אקראי של 32 בתים, בהרשאות `600`, ומוחרג מ־Git. הקוד אינו נכלל בתיעוד הזה.
3. אפשר להגדיר במקום הקובץ `CREATOR_INSIGHTS_ACCESS_TOKEN` ב־Streamlit secrets, בסביבת התהליך או ב־`.env`, לפי סדר קדימות זה. נדרש ערך אקראי URL-safe של 32–256 תווים.
4. החלפת תוכן קובץ הגישה נשמרת בהרשאות `600` ונבדקת ברענון הבא. שינוי `.env`/משתנה סביבה מחייב אתחול שרת. אפשר לייצר קוד באמצעות `python -c 'import secrets; print(secrets.token_urlsafe(32))'` — אין להעביר את הפלט לצ'אט או למאגר.

אם שרת היה פתוח לפני השינוי, אתחלו אותו כדי להחיל את `.streamlit/config.toml`. בסבב זה לא הופעל שרת חדש; הבדיקות השתמשו ב־AppTest. היישום חוסם כתובת האזנה שאינה loopback, השבתת CORS/XSRF או הפעלת static serving. הוגדרה רשימת Host מקומית. פרסום דרך reverse proxy/tunnel עדיין דורש TLS וניהול זהויות מתאים; בדיקת כתובת ההאזנה אינה מזהה את כל סוגי ההעברה הללו.

| פעולות יקרות | נעילה בין תהליכים ל־Flow המלא דרך UI/CLI ולכל שלבי הכנת snapshot; ניסיון חופף נדחה לפני קריאות הסוכנים |
| timeout | הרצת UI בקבוצת תהליכים; ב־macOS/Linux פקיעת הזמן עוצרת גם תהליכי משנה |
| יומנים | פלט גולמי זמני בהרשאות פרטיות; רק עד 1 MiB אחרון, לאחר סינון סודות מוכרים, נשמר ביומן UI פרטי; קריאת התצוגה מוגבלת |
| שגיאות Flow | סינון מפתחות ידועים לפני שמירת הודעות ביומן JSON; סינון נוסף לתצוגת היסטוריה קיימת |
| עיצוב | הורדת TOML מכילה רק `theme`, ללא הגדרות שרת/אימות; שמירה מקומית עדיין משמרת שאר הגדרות |
| מסירה | `train_model.py` מאמת fingerprint גם בהרצה ישירה |
| Supabase | תגובות במבנה לא תקין ו־URL/port פגומים הופכים לשגיאות בטוחות; redirects אינם נעקבים |
| סודות מקומיים | `.env` הקיים הוגבל ל־600; המפתח לא הוצג ולא הוחלף; קוד הגישה מוחרג מ־Git |

הנעילה אינה חלה על סקריפטים בודדים או קריאה ישירה ל־`CreatorInsightsFlow.kickoff()`; להרצה מלאה מתוך Python יש להשתמש ב־`run_project()`. אין בידוד תוצרים לכל ריצה, ולכן כשל באמצע עדיין יכול להשאיר תוצרים ישנים לצד חדשים. ניקוי היומנים הוא הגנה משלימה למפתחות מוכרים/פורמטים מזוהים, ואינו הוכחה שכל תוכן שרירותי נקי מסודות. אבטחת מחשב/חשבון בעל הפרויקט נשארת הנחת בסיס.

## סריקת תלויות — נותר לטיפול

`pip-audit` בדק את כל 159 הגרסאות הנעולות ב־`requirements.txt`, ללא חבילות שדולגו. נמצאו 6 רשומות התראה בשתי חבילות, שהן **5 התראות ייחודיות**; `PYSEC-2026-311` הופיע פעמיים. לא שונו גרסאות ולא הוסתרו התראות.

| חבילה | התראות ייחודיות | מצב |
|---|---|---|
| `mcp==1.28.1` | CVE-2026-59951 / GHSA-84m7-p3x7-pcfv | יש תיקון ב־1.30.0; CrewAI 1.15.28 דורש `mcp~=1.28.1` ולכן אינו תואם לשדרוג הזה |
| `chromadb==1.5.9` | CVE-2026-45829, CVE-2026-45833, CVE-2026-45831, CVE-2026-45830 | מאגר ההתראות אינו מציין גרסה מתוקנת; נדרש מעקב upstream |

התראת MCP נוגעת לניהול סשנים בשרת Streamable HTTP עם מצב. התראות Chroma עוסקות בשרתי האוסף, קוד embedding והרשאות בין tenants. בקוד הפרויקט לא נמצא שרת MCP/Chroma, אין הגדרת embedding מרוחק, ושני הצוותים מוגדרים `memory=False`. מכאן שלא הוכח מסלול ניצול במבנה הנוכחי, אך עצם התקנת החבילות נשארת סיכון תחזוקה. אין להפעיל שרתים כאלה מתוך הסביבה הנוכחית ללא טיפול ייעודי.

הניסיון לשדרוג נבחן מול metadata של החבילות: `~=1.28.1` דוחה `1.30.0`. גם גרסת CrewAI העדכנית שנבדקה ב־PyPI היא 1.15.28 עם אותה מגבלה. לכן לא נכפה עדכון באמצעות `--no-deps` שהיה יוצר סתירה במנהל החבילות. הפתרון הנדרש הוא שחרור CrewAI תואם או מעבר מבוקר לתשתית חלופית, עם בדיקות צוותים.

מקורות: [התראת MCP הרשמית](https://github.com/modelcontextprotocol/python-sdk/security/advisories/GHSA-84m7-p3x7-pcfv), [metadata של CrewAI](https://pypi.org/pypi/crewai/json), [דיווח Chroma במאגר הפרויקט](https://github.com/chroma-core/chroma/issues/6717), [התראת Chroma](https://github.com/advisories/GHSA-f4j7-r4q5-qw2c).

- `test_validation.py`: 5 עברו; `test_contract.py`: 6 עברו; `test_handoff_integrity.py`: תקין התקבל ושינוי נחסם; `test_flow_failure.py`: המידול נחסם בקלט לא תקין.
- `python -m pip check`: אין סתירות בין התלויות המותקנות.
- `git diff --check` ובדיקת קומפילציה עברו; קובצי הנתונים והמודל לא שונו.

לא בוצעו קריאות Claude, אימון אמיתי, הרצת תקיפה ממשתמש OS שני או בדיקה מול Supabase חי. בסקירת המקור לא נמצאו סודות בקבצים המנוהלים ב־Git, command injection, SQL injection, XSS מוכח או טעינה של pickle/joblib. המודל הבינארי נכתב אך אינו נטען בקוד הנוכחי. זה אינו מבטיח העדר כל חולשה.
